The Infrastructure Underneath

OpenAI's best models arrived on Google Cloud this week — a competitor's infrastructure — while a new research paper asked a question that becomes more important the more we treat AI as plumbing: when the tools an agent uses break, does a bigger, smarter AI cope better? The answer is no, and the reasons are worth understanding.

The one thing

OpenAI and Google announced that GPT-6 Astra, Sol, and Luna are now in private preview on Google Cloud's Model Garden — the marketplace where Google sells AI tools to enterprise customers. Google and Microsoft are each other's fiercest competitors, and Microsoft has been OpenAI's main partner since 2019, so this is genuinely unusual: like Coca-Cola agreeing to distribute through Pepsi's vending machines. Customers can now buy OpenAI's models on their Google Cloud bill, with data staying inside Google's servers. Microsoft remains OpenAI's primary partner, but the announcement signals something larger: frontier AI models are becoming commodity infrastructure — the kind of thing companies expect to be available everywhere, like a payment processor or a cloud database. General availability is expected in weeks.

Paper, explained: The bigger the model, the worse the crash

The Scaling Paradox of Tool-Calling LLM Agents Under Realistic MCP Faults · Iannillo et al. · NeurIPS 2026 · NeurIPS poster · arXiv 2610.32555

As AI agents become infrastructure — plugged into tools, databases, and services the way apps plug into payment APIs — a question becomes pressing: when one of those connections breaks, does a more capable model handle it better? This paper ran the experiment and got an uncomfortable answer.

The problem, and why it's hard

Modern AI agents don't just answer questions; they call tools. A research agent might query a database, run a code interpreter, and check a web search engine — all within a single task. The standard way these tools are connected is through a protocol called MCP (Model Context Protocol), originally developed by Anthropic and now widely adopted. When tools work perfectly, today's agents perform impressively. But tools don't always work perfectly. Servers time out. APIs return garbled data. A tool that worked yesterday is updated and its output format changes. These are the mundane realities of production software.

Most AI agent benchmarks ignore this entirely. They test agents in clean environments where every tool call succeeds. This is like testing a car only on a closed track, never on a road with potholes. The question the paper asks: what actually happens to agents when tools fail in the real ways they fail in the wild?

How it works

The researchers built something called MCP-Injector — think of it as a controlled fault machine that sits between an AI agent and its tools. Before building it, they did something clever: they mined 57,240 issue threads and pull requests from 1,774 real, open-source MCP tool repositories to catalog exactly how those tools actually fail in practice. From this they distilled six failure modes — including permanent tool unavailability, transient errors (it fails, then recovers), stale or outdated responses, and silent wrong answers (the tool returns something plausible but incorrect).

Here is the everyday analogy: imagine a new employee who has to use a filing system that occasionally gives them the wrong document with no warning, or a phone that sometimes doesn't ring, or a search tool that returns yesterday's results. The new employee has to notice these failures and route around them. MCP-Injector puts AI agents in this position, at controlled severity levels, with reproducible random seeds so experiments can be replicated.

What they actually did

The study ran 1,350 cells — crossing two backbone model sizes (a 20-billion-parameter model and a 120-billion-parameter model), three different agent harness configurations, and three fault-severity conditions (no faults, moderate faults, and heavy faults), each over multiple trials. The task suite covered practical multi-step tool-use scenarios: web research, code execution, document retrieval.

What they found

Under fault-free conditions, the 120B model outperformed the 20B model on task completion, as expected. But under realistic fault conditions, the 120B model's completion rate collapsed by roughly 60%, while the 20B model degraded less severely. The larger model ended up completing fewer tasks under faults than the smaller one, despite being more capable in ideal conditions. The researchers traced the cause to reasoning chain length: the 120B model, given its greater capability, generates longer, more elaborate reasoning steps before calling a tool. More steps means more opportunities for a mid-chain tool failure to corrupt the whole trace before the model notices and recovers. The smaller model, reasoning more tersely, is exposed to the fault window for less time.

The more important finding: across both model sizes, the agent harness — the framework code that wraps the model and handles tool calls — mattered more for fault tolerance than model scale. Harnesses with explicit retry logic and error-state handling recovered far better from faults than those without, regardless of the model inside.

The catch

The 1,350-cell study is substantial, but it covers two model sizes and three harnesses — not a comprehensive survey of the landscape. The six failure modes were mined from open-source MCP repositories; proprietary enterprise tooling may fail differently. And the task suite, while practical, is not exhaustive. The paper does not claim to explain every failure mode, only to establish that the problem is real and that naive assumptions (bigger model = more robust) are wrong.

If you remember one thing: A more capable AI agent is not automatically a more resilient one — when the tools it depends on break, longer reasoning chains can make failures worse, and the wrapper code around the model matters more than the model itself.

Why it matters

Two of this week's biggest stories point in the same direction, and the paper points at what neither announcement addresses. OpenAI distributing through Google Cloud, Replit switching its AI spend, Kimi open-weighting its flagship model — all of it treats AI capability as a commodity that flows freely between platforms. That is probably the right direction. But the paper on MCP fault tolerance is a reminder that "AI as infrastructure" carries the same failure modes as all infrastructure: the more tightly it is woven into other systems, the more quietly things can go wrong when one thread breaks. The Financial Stability Board named concentration risk this week; the researchers named a different risk — resilience to the inevitable faults in any complex networked system. As agents grow more capable, the wrapper around them matters just as much as what's inside.

Decoder

Word of the day
MCP (Model Context Protocol)
The standard "plug" that connects an AI agent to external tools — databases, web browsers, code runners, APIs. Originally created by Anthropic, now widely adopted. Think of it as the USB standard for AI tools: any tool that speaks MCP can work with any agent that also speaks MCP. The paper this issue explains what happens when the plug sparks.
Fault injection
A testing technique where you deliberately cause a failure — a timeout, a wrong answer, an unavailable server — to see how a system responds. Engineers use it to find brittle assumptions before real failures do.
Reasoning chain
The internal step-by-step working a language model produces before giving a final answer. Longer chains mean more thorough reasoning but also more steps at which something can go wrong — the paper's core finding.
Harness
The framework code that wraps an AI model and manages its interactions with tools, memory, and other agents. Two models with the same weights but different harnesses can behave very differently — especially under failures.
Scaling paradox
When a larger, more capable model performs worse than a smaller one on the same task due to an unexpected side effect of its extra capability. Here: longer reasoning chains create more exposure to tool failures.
Fault tolerance
A system's ability to keep working despite individual component failures. The internet was designed this way from the start — traffic reroutes around broken links automatically. AI agent frameworks mostly were not.
