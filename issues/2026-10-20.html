Blueprints That Learn

OpenAI's most capable model learned to split work among multiple agents running at the same time. DeepSeek refreshed its open-weight Flash model under a fully permissive licence. And a Google paper published this month quietly asked a question worth sitting with: what if an AI system's operating instructions could rewrite themselves, getting a little better with every task they touch?

The one thing

On October 16, OpenAI added parallel agents to GPT-6 Pro in ChatGPT. Instead of one agent working through a task from start to finish, Pro subscribers can now watch multiple agents tackle different subtasks simultaneously — each reporting back when done, each inspectable. Users can open a completed subtask and read its work. OpenAI describes this as multiple agents working on different parts of a problem at once, with progress shown live. It's the first time a mainstream consumer product has made multi-agent execution not just usable but visible: you're watching a team work, not reading a finished report. The company has not published figures on speed or quality gains from the feature.

Paper, explained: the wrapper that teaches itself

Harness²: Recursive Agent Harnessing for an Open World · Ruiyao Xu, Yanfei Chen, et al. (Google Cloud AI Research & Northwestern University) · arXiv 2610.14224, Oct 9, 2026 · github.com/google-research/harness2

Issue №1 of this magazine used the word "harness" in its very last sentence. It has come up in almost every issue since. This week a team at Google published a paper that might change how harnesses are built — by letting them build themselves.

The problem, and why it's hard

When an AI agent is sent to do a job — research a topic, help debug a codebase, manage a workflow — it arrives with a set of instructions baked in. Which tools to call, how to break a big task into steps, how to handle errors and dead ends. This wrapper of rules and logic is the harness. Engineers write it by hand, before any real tasks have been run. The trouble is that open-world tasks — the actual things users send — weren't in the room when the harness was designed. A task about something that emerged last month, or a codebase that never existed before, can strain the harness in ways its authors didn't anticipate. And there is a deeper snag: how do you know which edits to the harness would actually help? In a closed benchmark you have a right answer to check against. In the open world, there's no ground-truth teacher watching. So you can't simply try variations and keep the best one, because "best" has no definition yet.

How it works

Think of a visiting chef arriving at a kitchen they've never worked in before. They read the house recipe (the harness), start cooking, and immediately run into small mismatches: the oven runs a little hot, the ingredient labeling is inconsistent, one step assumes equipment that's stored elsewhere. They don't rewrite the recipe from scratch — that would lose everything that already works. Instead, they note what caused friction, make targeted adjustments, and leave a slightly better recipe at the end of service, ready for the next chef. Harness² runs exactly this loop, but twice over — one inside the other.

The inner loop runs at the task level. When a new task arrives, the system proposes several candidate edits to the current harness — small adjustments to instructions, tool-call sequences, or error-handling logic. It then probes each candidate by actually running it on part of the task and collecting execution traces. Finally, it composes — picks the elements that worked best across those runs and assembles them into an improved harness for finishing this task. This Propose-Probe-Compose sequence can repeat multiple times within one task, with each pass building on the last.

The outer loop runs at the harness level. This is the chef writing up revised kitchen notes to take home for next week. After each task, the lessons from the inner loop get folded into a persistent harness that becomes the starting point for all future tasks. No task has to start from a blank slate; every completed job makes the baseline a little more capable for the next one.

What they actually did

The researchers tested Harness² on two frozen language models — GLM-5 and Gemini 3.5 Flash — across three benchmarks: WorkBuddy-Bench (office-style tasks: scheduling, summarising, data lookup), JobBench (longer multi-step work tasks), and LAB (lab research assistant tasks, the hardest of the three). "Frozen" is the critical detail: the underlying model weights were never changed. Only the harness was allowed to evolve. This rules out the explanation that gains came from fine-tuning; the improvement is entirely in the wrapper, not the engine.

What they found

Harness² improved both models on all three benchmarks. The numbers: +11.5 percentage points on WorkBuddy-Bench, +4.5 on JobBench, and +11.8 on LAB — with the largest gains on the hardest tasks. Performance kept climbing as the budget for task-level recursion steps increased, suggesting the system hadn't hit a ceiling within the tested range. The outer loop also worked: a harness shaped by earlier tasks consistently outperformed one reset to the original, confirming that lessons genuinely carry over rather than cancelling out.

The system ran in both sequential and parallel modes — you can test candidates one after another, or run them all at once if compute is available, with parallel being faster and reaching the same quality.

The catch

The benchmarks are tidy, closed environments with clear success signals — the opposite of the "open world" the title promises. In real deployment, you rarely have a reliable way to measure whether a harness edit was an improvement, which is exactly the problem the paper was motivated by but doesn't fully solve. The comparisons are also self-referential: Harness² is measured against each model's own baseline harness, not against a hand-crafted specialist harness built by a dedicated engineering team. The compute cost of running multiple probes per task is noted but not quantified for production use.

If you remember one thing: A model can get measurably better at its job — double-digit improvements on hard tasks — without any change to the model itself. The lever is the instructions wrapped around it.

Why it matters

The GPT-6 Pro parallel agents feature and the Harness² paper are both pointing at the same thing from different angles. One is a product decision — let users watch multiple agents run at once. The other is a research result — let the harness itself improve with each task, automatically. Together they suggest that the limiting factor for what AI agents can usefully do is shifting away from the model's raw capability and toward the design of the system around the model: how tasks are decomposed, what instructions are given, how failures are handled. Engineers currently maintain those systems by hand, updating them slowly based on observation. If that process can be made recursive — if the wrapper can tighten itself task by task — agents could grow specialised far faster than any team could manually maintain them. That's not a product announcement. It's a change in how the thing improves.

Decoder

Word of the day
Harness
In AI, a harness is the scaffolding around a model: the system prompt, tool definitions, memory setup, error-handling logic, and workflow rules that shape how it behaves. If the model is the engine, the harness is the car — the thing you actually drive to a destination. A better engine helps, but the right car matters too.
Propose-Probe-Compose
The three-step inner loop in Harness²: draft candidate edits to the harness (propose), test each one on the actual task (probe), then combine the best-performing elements into a new harness (compose).
Mixture of experts (MoE)
A model architecture with many specialist sub-networks ("experts"), where only a few activate for any given input. DeepSeek V4.1-Flash has roughly 763 billion total parameters but only about 8 billion active at once — far cheaper to run than a dense model of the same total size.
Context window
The maximum text a model can hold in working memory at once. One million tokens is roughly 750,000 words — about ten full novels — which is why a 1M-token window is considered very large.
Open weight
A model whose trained parameters are published for anyone to download, run, or fine-tune. Not the same as open source, which usually also means the training code and data are public. DeepSeek V4.1-Flash ships under the MIT licence — the most permissive category.
Parallel agents
Multiple AI instances running simultaneously on separate subtasks, coordinated by a central system. Faster than a single agent working step by step, and now a live feature in GPT-6 Pro.
