The One That Lives Here

Two things moved this week that point in the same direction: smaller, cheaper, more under your control. Anthropic's newest compact model is the first of its kind with an adjustable thinking level. And the week's most-upvoted research paper asks a different version of the same question — does your AI assistant have to live in a company's data center at all?

The one thing

Claude Haiku 5.5 arrived Tuesday — Anthropic's fastest model, and the first Haiku ever to ship with a variable effort setting. Dial it up and the model takes a moment to reason before answering; leave it at the default and it fires back immediately. The context window — how much text it can hold at once — jumped from 200 thousand tokens to one million. The price dropped to $0.10 per million input tokens, one-tenth of the model it replaces. It targets the kind of work that runs constantly in the background: summarising, classifying, piloting a browser, acting as a quick helper inside a larger pipeline. Benchmark scores on Anthropic's own computer-use test climbed from 15.7% to 72.4% against the prior Haiku, a substantial leap for such a small model. The effort dial is the first of its kind in the Haiku line, and lets developers calibrate thinking depth per request rather than picking a different model entirely.

Paper, explained: your AI agent as a tenant, not a guest

"nanoMuse: An Open-Source Personal Agent for Every Device You Own" · Guangyi Liu, Yong Liu, Jiangning Zhang · arXiv 2610.08699

The most-upvoted paper on Hugging Face this week is not about a bigger model or a harder benchmark. It is about where your AI agent lives — and who decides what it can touch.

The problem, and why it's hard

Every major AI assistant product today makes the same architectural choice: the agent runs on the company's servers, not yours. Your phone is a window into someone else's computer. That choice is understandable — running capable AI locally is expensive, and coordinating a conversation across a laptop, a phone, and a tablet is technically awkward. But it means every screenshot, every file the agent reads, and every action it takes is visible to the company running the cloud. The paper's direct example is Meta's Muse agent, whose logic runs in closed, vendor-hosted Linux virtual machines with only a small SDK opened to developers. nanoMuse's authors call this the "absent owner" model: the infrastructure belongs to someone else, and the user is a guest.

The harder problem, once you decide to put the agent on the user's devices, is trust. A personal agent that controls your screen, opens your files, and sends messages on your behalf needs to behave predictably even when you are not watching. That requires some principled way to decide, locally, what the agent is and is not allowed to do.

How it works

The architecture the paper proposes sits on a simple idea: put a doorman inside the building, not outside it. The doorman is a component called the Sentinel, which runs on the user's device and sits between the agent and anything it wants to touch — the screen, the file system, the microphone, outbound messages. Every action the agent proposes passes through Sentinel first.

Think of it like a hotel key system. In a regular hotel, the front desk (the cloud company) controls which doors open. In nanoMuse's model, you own a master key on your device, and the Sentinel is the physical lock on each door. The front desk is optional — or you can replace it entirely. Sentinel classifies each proposed action by risk level, checks it against a mode the user has set (cautious, standard, or permissive), and either proceeds, warns, or blocks. Approvals can be one-time, per conversation, or permanent for a trusted target. Crucially, everything is logged locally in plain text — not uploaded anywhere.

Memory works the same way. Instead of a user profile stored in a company's database, nanoMuse stores its memory of the user as a set of plain, editable text files on the device: a profile file, an identity file, routines. The user can open those files, read them, and change them directly. There is no hidden representation that would require the company's tools to inspect.

Coordination across devices goes through a relay — a small server that keeps one conversation thread consistent across a person's phone, laptop, and tablet. The relay can be self-hosted by anyone, and the paper provides a reference implementation. A free relay allowance covers users who do not want to run their own. The agent itself uses whichever model the user chooses: any cloud API key, or a locally-running model for users who want zero cloud involvement.

What they actually did

The paper, arXiv 2610.08699, was released on October 6 alongside version 1.0.0 of working software. Apps are available for Android, macOS, Windows, Linux, and a web interface, with iOS and iPadOS in TestFlight beta (Apple's tighter sandboxing limits what the agent can control on iPhone). The project is GPL-3.0 open source, meaning anyone can read the code, modify it, and run their own version — but if they build on it, they have to open that derivative work too. The paper evaluates the Sentinel's accuracy at classifying action risk — specifically whether it correctly flags high-risk operations like sending email, deleting files, or granting new permissions. The authors report the classification results but did not publish a single headline benchmark score; the work is positioned as a design paper with a working artefact rather than a performance-comparison paper.

What they found

The paper's main claim is architectural: that you can build a cross-device personal agent with device-local control, user-auditable memory, and no mandatory cloud dependency, and ship it as consumer software in a single release. The Sentinel's risk-classification approach was evaluated against a set of simulated agent trajectories across each platform; the paper reports that destructive and permission-granting actions were correctly blocked in the majority of test cases, with the iOS version showing lower coverage due to sandboxing. Memory files were shown to remain consistent across devices within a relay session. The screen-control "hands" — the code that actually moves the pointer and types — are acknowledged as the weakest link: fragile across app updates, limited on iOS, and not yet evaluated on a standardised benchmark.

The catch

The paper itself is honest about several limits. First, screen control is brittle — app interfaces change, and the agent's ability to navigate them breaks in unpredictable ways. Second, running on-device does not mean safe: a user who grants the agent broad permissions is no safer than if the agent were in the cloud; the Sentinel just makes those permissions explicit. Third, the relay, even self-hosted, is a single point of failure for cross-device coordination. And fourth, none of this solves the model itself: a user who routes through a cloud API key is still sending their prompts to that provider, even if the Sentinel and memory stay local.

If you remember one thing: Your AI agent does not have to live in a company's data center — this paper ships working code that proves the alternative is buildable today.

Why it matters

Claude Haiku 5.5 and nanoMuse are not the same kind of story, but they are pulling in the same direction. Haiku 5.5's effort dial means the capabilities once reserved for expensive flagship models are now available at the cheap, fast tier — the tier that gets deployed at volume in the background tasks ordinary people never see. nanoMuse points to a future where the agent itself, not just the model, can be moved onto hardware you control. Together they sketch a picture of a technology that is distributing its power downward and outward: not just cheaper per token, but more controllable, more local, and less dependent on a small number of infrastructure owners. That distribution is where the most interesting decisions about AI will be made in the next couple of years — not at the frontier, but in how far the frontier reaches.

Decoder

Word of the day
Effort control
The ability to tell a model how hard to think before answering — low effort means a quick, direct reply; high effort means the model reasons through the problem before responding. Think of it like asking someone a question: you can ask for their first instinct or ask them to sleep on it. Haiku 5.5 is the first compact model to offer this as an adjustable dial per request, rather than requiring you to pick a different, slower model entirely.
Sentinel
In nanoMuse, a software gate that runs locally on your device and checks every action the AI agent proposes against rules you have set. Nothing the agent does to your screen, files, or messages passes without Sentinel's sign-off.
Relay
A lightweight server that keeps a single conversation consistent across multiple devices. In nanoMuse you can run your own relay — or use the project's free one — so your phone and laptop share the same context without involving a cloud provider.
GPL-3.0
A software licence that lets anyone use, copy, and modify code freely, but requires that any derivative work also be released under the same open terms. Used by nanoMuse; means neither a company nor a developer can take the code private.
Context window
How much text an AI model can hold in active attention at once. Haiku 5.5's jumped from 200 thousand to one million tokens — roughly the equivalent of going from holding one novel in mind to holding five.
Diffusion transformer
An architecture that starts from noise and gradually refines it into a finished output — video, image, or audio — using the same attention mechanism that powers language models. Kandinsky 6.0 uses one to jointly generate video frames and audio waveforms in a single pass.
